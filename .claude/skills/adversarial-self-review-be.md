# 🧐 스킬: 백엔드 적대적 셀프 리뷰 (Adversarial Self-Review - BE)

**전체 파일이 아니라 `git diff`(staged, 마지막 커밋 대비)만 본다.** 4단계를 순서대로, 각 단계는 앞 단계 결과를 넘겨받아 진행한다(마지막 종합 단계에서 1~3을 다시 훑을 기회를 준다).

각 단계에서 실패(위반 사항 발견) 시 성공할 때까지 반드시 코드 수정 후 해당 단계부터 다시 Loop를 돌며, 성공해야만 다음 단계로 넘어간다.

## 1단계 — 임팩트 조사 + 버그/취약점
- 이 `git diff`가 바꾸는 메서드/클래스를 호출하는 다른 곳(같은 모듈 내)에 영향이 있는지 추적.
- 버그: null 처리, 경계값, 예외 분기 빠짐.
- 취약점: 인증/인가 누락 (Gateway 및 Interceptor 연동), 인젝션, 민감정보 노출.

## 2단계 — 코드 스타일 / 네이밍 / 재사용성
- `architecture.md` 기준으로 이름 하나씩 대조 (예: Service의 `get` 접두사 준수 여부).
- 같은 모듈의 기존 코드와 스타일이 어긋나는 지점 (예: 기존의 `AbstractServiceTest` 인프라를 따르는가).
- 이미 있는 로직을 새로 복제해서 짠 부분(재사용 실패).
- file → method → line 단위로 훑는다 — 파일 훑고 끝내지 않는다.

## 3단계 — 레이어 책임 준수 / 코드 흐름 / 효율성
- `architecture.md`의 계층 규칙을 벗어난 곳 (예: Controller에 비즈니스 로직 존재, Service에 DTO 반환 로직 존재).
- 코드 흐름이 자연스러운지 (조기 반환 대신 중첩 분기 남발 등).
- `architecture.md` 기준 효율성 (JPA N+1 문제, 불필요하게 넓은 트랜잭션, 동적 프로젝션 미사용 및 `nativeQuery` 사용 여부).

## 4단계 — 종합조사 및 검토
- `diff` 에 대해 1~3단계의 맥락을 모아 전체적 종합 검토 수행.
- 터미널 단위 테스트(`mvn test`) 파이프라인 통과 여부 최종 점검.
